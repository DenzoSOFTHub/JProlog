## CRITICAL (2)

### 1. [CLP(FD)] Global singleton ConstraintStore is never reset, leaking domains/constraints across queries and across independent Prolog instances
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/clpfd/ConstraintStore.java:11-21, 598-601`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: ConstraintStore is a JVM-wide singleton keyed by raw Prolog variable NAMES (e.g. "X", "V"). clear() exists but is never called from anywhere outside the class (grep over src/main shows no external caller; Prolog.java never references ConstraintStore). Therefore domains and constraints from one query persist into the next, and even into a brand-new `new Prolog()` engine. Empirically verified: p1.solve("V in 1..3, V #= 2, fd_dom(V,D)") then a FRESH p2.solve("fd_dom(V,D)") returns D=[2] (leaked). Running the SAME query twice gives different results: "C in 1..2, D in 1..2, C #\\= D, label([C,D])" returns 2 solutions on a clean store but 0 solutions after prior unrelated queries polluted the store. Because clauses are reused and the store is shared mutable static state, this is also a thread-safety hazard: two engines/threads corrupt each other's domains. Variable names are not query-unique (a user reusing X across goals, or TermCopier producing the same `_R..` names, collide).
- **Fix**: Make the constraint store per-query (or per-Prolog-engine / per-solver) state instead of a static singleton, and key it by a unique variable identity (e.g. the Variable object or a per-query fresh id), not the textual name. At minimum, clear the store at the start of every top-level solve() (Prolog.solve) and after it completes, and scope temp-var names per query. Long term, attach the FD store to the QuerySolver/engine and pass it through context so concurrent engines are isolated.

### 2. [List/String/Atom builtins] append/3 throws on ordinary list concatenation when an element is an unbound variable
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/list/Append.java:28-34`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: The concatenate mode is gated on list1.isGround() && list2.isGround(), which is a DEEP groundness check on the elements, not a structural (spine-closed / proper-list) check. As a result the most common append mode fails whenever any element is an unbound variable. Verified at runtime: append([a],[X],R) throws; append([a,b],[c,Z],R) throws; append([X],[Y],R) throws. Only fully-ground lists work (append([a],[b],R) => R=[a,b]). This breaks an enormous class of ordinary programs (building lists that contain logic variables). The same root cause makes the split mode (handleSplit, gated on result.isGround()) reject append([a|T],B,[a,b,X]).
- **Fix**: Replace the isGround() guards with a proper-list (closed spine) test. Add a helper isProperList(Term) that walks .(H,T) chains to []. Use mode selection: if list1 and list2 are proper lists -> concatenate (extractElements works on the spine and keeps element variables); else if result is a proper list -> split. handleConcatenate/extractElements already only walk the spine, so simply changing the guard from isGround() to isProperList() makes append([a],[X],R) succeed with R=[a,X].


## HIGH (32)

### 3. [Arithmetic] (**)/2 returns integer for integer operands instead of float (ISO violation)
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/ArithmeticEvaluator.java:524-529`  ·  **Category**: iso-conformance  ·  **Confidence**: high
- **Problem**: Per ISO 13211-1 §9.3.1, (**)/2 is the floating-point power function and ALWAYS returns a float, even for integer operands (e.g. `X is 2**3` must give 8.0). Only (^)/2 (§9.3.10) returns an integer for integer operands. Here `**` is routed to integerPower() exactly like `^`, so `2 ** 3` yields integer 8 instead of float 8.0. Verified at runtime: `X is 2 ** 3 => X=8(int)` and `X is 0 ** 0 => X=1(int)`. SWI-Prolog and any ISO system return 8.0. This silently changes result types of downstream computations and breaks portability.
- **Fix**: Remove `**` from the integer switch in applyBinaryToNumber (and do not let it reach integerPower for integer operands). Route `**` always to the float path: `case "**": return new Number(Math.pow(left.doubleValue(), right.doubleValue()), false);` keeping the existing 0.0**negative -> evaluation_error guard. Leave `^` calling integerPower.

### 4. [Arithmetic] truncate/round/integer/floor/ceiling silently clamp out-of-long-range floats to Long.MAX_VALUE
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/ArithmeticEvaluator.java:457-463`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: These integer-producing rounding functions convert the double result with a raw `(long) result` cast. For magnitudes above 2^63 the cast saturates to Long.MAX_VALUE (or MIN_VALUE), producing a wrong integer instead of the mathematically correct (big) integer. Verified: `X is truncate(1.0e19) => 9223372036854775807`, `X is round(1.0e19) => 9223372036854775807`, `X is floor/ceiling/integer(1.0e19)` all give the clamped value rather than 10000000000000000000. ISO §9.1.6.x require the exact integer value (which JProlog can represent via BigInteger elsewhere). Soundness bug: `floor(1.0e19) =:= 1.0e19` would then be false.
- **Fix**: Convert the rounded double through BigInteger to avoid clamping, e.g. `double r = function.apply(arg.doubleValue()); return normalizeBigInt(new java.math.BigDecimal(r).toBigInteger());` (or for round, apply the rounding first then BigDecimal). Reuse normalizeBigInt() so small results still come back as long.

### 5. [Arithmetic] Integer-only operators (mod, rem, //, div, <<, >>, /\, \/, xor) silently accept float arguments instead of type_error(integer, ...)
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/ArithmeticEvaluator.java:557-570`  ·  **Category**: iso-conformance  ·  **Confidence**: high
- **Problem**: ISO 13211-1 requires mod/2, rem/2, (//)/2, div/2, the bitwise ops (/\, \/, xor, \) and shifts (<<, >>) to take integer arguments; a float argument must raise type_error(integer, Float). Here, when at least one operand is a float, the code silently truncates both operands to double and casts the result to long. Verified: `X is 10.5 mod 3 => 1`, `X is 10 mod 3.0 => 1`, `X is 10.0 rem 3 => 1`, `X is 10.0 // 3 => 3`, `X is 5.0 /\ 3 => 1`, `X is 5.0 << 2 => 20`. All should throw type_error(integer, 10.5)/etc. This both hides programmer errors and gives non-portable answers.
- **Fix**: Before the float-coercing branch, validate operands: if name is in INTEGER_BINARY_OPS and either left or right is not an integer, throw `new PrologException(ISOErrorTerms.typeError("integer", <the float Number>, "("+name+")/2"))`. Only fall through to the long computation when both operands are integers (in which case they should already have been handled by the bothInteger switch).

### 6. [CLP(FD)] indomain/1 ignores all posted constraints, producing unsound solutions
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/clpfd/ClpfdPredicates.java:524-547`  ·  **Category**: bug  ·  **Confidence**: high  ·  (orig sev: critical)
- **Problem**: executeIndomain enumerates the variable's domain and emits every value as a solution WITHOUT assigning the value into the store and re-propagating, and without checking any constraint that links the variable to others. So `X in 1..3, Y in 1..3, X #< Y, indomain(X), indomain(Y)` yields {X=2,Y=2} which violates X #< Y (empirically reproduced: 4 solutions including {X=2,Y=2}). indomain must behave like a one-variable labeling step: for each candidate value, set the domain to the singleton, propagate(), and only succeed if propagation does not wipe out any domain. As written it is unsound whenever the variable participates in a constraint that is not already bounds-entailed.
- **Fix**: Reimplement indomain to snapshot the store, then for each value v in the domain: setDomainValues(var,{v}); if propagate() succeeds and no domain is wiped out, emit a solution that reflects the propagated singletons of all linked vars; restore the snapshot before trying the next value. Equivalent to doLabeling on a single-variable list.

### 7. [CLP(FD)] #\= (disequality) between two non-singleton variables performs no propagation at any stage
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/clpfd/ConstraintStore.java:300-347, 666-694`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: NEQ only prunes when one side is a singleton AND the value is at a domain boundary (bounds pass), or in the AC-3 holds() pass it filters element-wise but NEQ-holds(l,r) is satisfiable for almost any pair so it never removes anything until a domain is a singleton. There is no mechanism that prevents two variables with overlapping multi-value domains from later being labeled to the same value when the user does not use label/labeling (e.g. uses indomain). Combined with the indomain bug, `C in 1..2, D in 1..2, C #\= D, indomain(C), indomain(D)` yields {C=1,D=1} and {C=2,D=2} (empirically 4 unsound solutions). Even with label/2 it works only because labeling re-propagates after each assignment; the constraint itself is a no-op until singletons appear. NEQ that removes a singleton value only when it is at a boundary is also incomplete: removing an interior value cannot tighten bounds, so this is fine for bounds-consistency, but the constraint must still be re-checked/enforced at assignment time.
- **Fix**: Ensure NEQ is enforced whenever either side becomes a singleton (the AC-3 holds() path already removes the singleton value from the other domain; make sure the constraint is re-awoken after any narrowing that creates a singleton). Critically, make indomain/labeling re-propagate so NEQ takes effect at assignment time. Do not rely solely on the boundary-only bounds rule for correctness.

### 8. [CLP(FD)] ADD/SUB bounds inference uses int arithmetic and silently overflows (MUL correctly uses long)
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/clpfd/ConstraintStore.java:398-400, 410-411, 424-425, 433-434, 443-444, 456-457`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: In propagateArithmeticBounds the ADD and SUB cases compute bound sums/differences in int (e.g. exprLeftMax + exprRightMax, resMin - exprRightMax). When operands are near Integer.MAX/MIN these expressions overflow and wrap around, yielding bogus bounds that can wrongly prune or wrongly retain values (unsound). The MUL case at lines 464-475 deliberately uses long and clamps to int range, so the inconsistency is clearly an oversight. Empirically, `X in 2000000000..2000000000, Y in 2000000000..2000000000, Z #= X+Y` produces 0 solutions; 2e9+2e9 overflows int (wraps negative), so the result interval is computed incorrectly rather than handled as out-of-range. Note ArithmeticConstraint.compute() (lines 909-920) DOES guard overflow with long, so the AC-3 path and the bounds path disagree.
- **Fix**: Compute all ADD/SUB bound combinations in long, then clamp to [Integer.MIN_VALUE, Integer.MAX_VALUE] (or treat any out-of-range bound as an unbounded/empty interval) before calling narrowDomain, mirroring the MUL case. Add a saturating helper for +/- like the existing clamp for *.

### 9. [CLP(FD)] Finite domains are fully enumerated as TreeSet<Integer>, causing OutOfMemoryError on large ranges
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/clpfd/ConstraintStore.java:28-34`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: Every domain is materialized as an explicit TreeSet of boxed Integers. A perfectly legal goal like `X in -3..2147483647` allocates ~2.1 billion Integer objects and throws OutOfMemoryError (empirically reproduced: `X in -3..2147483647, X #=< 2147483647, fd_size(X,S)` crashes with java.lang.OutOfMemoryError: Java heap space). The same enumeration happens in ClpfdPredicates.parseDomain (lines 136-139) and in ensureDomainFromExpr default fallback. Real CLP(FD) usage frequently involves wide initial domains (0..sup, 1..N for large N), so this is a practical DoS, not a corner case. Also makes propagation O(domain size) per step.
- **Fix**: Represent domains as a sorted set of intervals (e.g. a list/tree of [lo,hi] ranges) rather than enumerating every value. Bounds-consistency narrowing (headSet/tailSet) then becomes O(log) interval splits and AC-3 element filtering can iterate ranges. At minimum, cap or reject domain ranges above a configurable size with a representation_error / resource_error instead of OOMing the JVM.

### 10. [Concurrency/debug] ConcurrentPredicates runs parallel goals on a single shared QuerySolver whose mutable instance fields (recursionDepth, currentCutStatus, module context) race
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/threading/ConcurrentPredicates.java:122-126, 164-167, 211-219, 275-283, 326-334, 390-393, 429-434`  ·  **Category**: thread-safety  ·  **Confidence**: high  ·  (orig sev: critical)
- **Problem**: Every concurrent predicate submits worker tasks that all call the *same* QuerySolver instance (ide.getPrologEngine().getQuerySolver() — a single instance per Prolog engine, Prolog.java:58). QuerySolver is documented and implemented as single-threaded: it holds mutable, non-synchronized, non-volatile instance fields that solve() reads and writes on every call: `private int recursionDepth` (QuerySolver.java:158, incremented/decremented at 213/217 with no sync), `currentCutStatus` (saved/restored at 427-432), `currentModuleContext` (line 27) and `callerModuleContext` (line 30). When N goals run in parallel on this shared solver, recursionDepth++/-- is a non-atomic read-modify-write executed by multiple threads, so the count is corrupted: it can spuriously exceed MAX_RECURSION_DEPTH (2000) and throw a bogus resource_error(max_recursion_depth) for shallow goals, or never decrement back to 0 and poison subsequent queries; currentCutStatus save/restore from one thread clobbers another thread's cut state, producing unsound cut behaviour. The class header comment claims 'QuerySolver.solve() is reentrant for read-only KB access' — KB access is indeed defensively copied/synchronized (KnowledgeBase.java), but the solver's own scalar fields are not, so the reentrancy claim is false for parallel use.
- **Fix**: Do not share one QuerySolver across threads. Either (a) give each worker task its own QuerySolver bound to the same KnowledgeBase/BuiltInRegistry (cheap to construct), e.g. `QuerySolver worker = new QuerySolver(kb, registry); worker.setPrologContext(...)` per task; or (b) make the per-query mutable state (recursionDepth, currentCutStatus, module contexts) ThreadLocal in QuerySolver. Option (a) is cleanest and matches the intended isolation. Until fixed, document that concurrent_* predicates are unsound.

### 11. [DCG] DCG cut `!` is mistranslated into a non-terminal `!/2`, silently breaking difference-list threading and cut commitment
- **File**: `src/main/java/it/denzosoft/jprolog/core/dcg/DCGTransformer.java:95-106, 138-141`  ·  **Category**: bug  ·  **Confidence**: high  ·  (orig sev: critical)
- **Problem**: `!` parses as an Atom (verified: '!' -> Atom name=!), so the `case "!"` inside the `body instanceof CompoundTerm` switch (lines 117-159) is DEAD CODE. A cut in a DCG body therefore falls into the atom `else` branch (line 103-105) and is emitted as the non-terminal goal `!(Input, Output)`. At solve time QuerySolver.handleBuiltIn line 415 (`if ("cut".equals(name) || "!".equals(name))`) matches on name only and treats `!(S1,S2)` as a plain cut, ignoring the two arguments, so the required `S1 = S2` unification is NEVER performed. The difference list is severed across the cut. Verified at runtime: for `cuttest --> [a], !, [b].` the transformed body is `[=(_S0,[a|_S1]), !(_S1,_S2), =(_S2,[b|_S])]`, and `phrase(cuttest,[a,c])` wrongly SUCCEEDS with `_S1=[c]`, `_S2=[b]` (S1 != S2). The correct ISO answer is FAIL, because after `[a]` the remainder is `[c]`, `!` commits, and `[b]` cannot match `[c]`. The dropped threading lets `[b]` match a fresh unbound tail and silently discards the real remaining input.
- **Fix**: Handle `!` in the atom branch of transformBody, producing the standard expansion `(Input = Output, !)` so the difference list is threaded AND the cut still fires. Add before the final `else`: `else if ("!".equals(atomName)) { return TermUtils.createCompound(",", TermUtils.createCompound("=", input, output), new Atom("!")); }`. (The dead `case "!"` in the compound switch can then be removed.) Also handle the control atoms `true`/`fail` similarly if desired (`true` -> `Input=Output`). Verified: applying this expansion makes `phrase(cuttest,[a,c])` fail as required.

### 12. [DCG] phrase/2 and phrase/3 return only the first solution, making DCG parsing non-backtrackable and incomplete
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/dcg/Phrase.java:86-112, 38-59`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: `phrase3` collects every solution from the solver into `solutionList`, but then commits only `solutionList.get(0)` and returns a single boolean. `executeWithContext` mirrors this by adding exactly one binding map to `solutions`. As a result `phrase/2` and `phrase/3` are effectively `once(phrase(...))` — they cannot enumerate alternative parses or alternative `Rest` splittings on backtracking. Verified at runtime: with `ab --> [a].` and `ab --> [a,b].`, the query `phrase(ab,[a,b],R)` returns only 1 solution (`R=[b]`), whereas the correct answer set is two solutions `R=[b]` and `R=[]`. This is a soundness/completeness defect for any non-deterministic grammar (the common idiom of using DCGs as generators or splitters is broken). Other BuiltInWithContext predicates such as Conjunction add ALL solution maps to `solutions`, which is the correct pattern.
- **Fix**: Make phrase a multi-solution predicate. In executeWithContext, build the expanded DCG goal and call `solver.solve(goal, copyOf(bindings), solutions, CutStatus.notOccurred())` so every solution map from the solver is added directly to the caller's `solutions` list (as Conjunction does), instead of routing through the single-boolean `solve()`/`get(0)` path. Remove the `solutionList.get(0)`-only merge.

### 13. [DCG] call_dcg/3 is a broken stub that ignores the DCG body and just unifies Input with Output
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/dcg/DCGUtils.java:18-39`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: `call_dcg/3` is registered as a live built-in (BuiltInFactory line 360: `registerFactory("call_dcg", DCGUtils.CallDCG::new)`) but its implementation completely ignores `dcgBody` and merely unifies the input and output difference-list terms. It never expands or solves the DCG body. Verified at runtime: with `lit --> [x].`, the query `call_dcg(lit,[x],R)` returns `R=[x]` (i.e. it asserts Input=Output), whereas the correct result is `R=[]` after consuming `x` via the `lit` rule. Any program relying on call_dcg/3 (the SWI primitive that phrase/3 itself is defined in terms of) gets silently wrong parses.
- **Fix**: Implement CallDCG as a BuiltInWithContext: expand `dcgBody` with the input/output terms using the same logic as the DCG body transformer (reuse DCGTransformer's body-expansion, or build `phrase(Body, Input, Output)`), then call `solver.solve(...)` and propagate all solutions. If a full implementation is not feasible now, at minimum delegate to the same expansion used by phrase/3 rather than unifying Input=Output. Alternatively, unregister call_dcg/3 until correctly implemented to avoid silently wrong answers.

### 14. [Exceptions/ISO errors] Arithmetic comparison predicates destroy ISO error terms by re-wrapping every exception in a bare-atom message

} catch (PrologException e) {

### 15. [Exceptions/ISO errors] Unbound variable in arithmetic raises bare atom instead of ISO error(instantiation_error, _)

### 16. [Exceptions/ISO errors] Unknown arithmetic function and non-evaluable term raise bare atoms instead of ISO type_error(evaluable, Name/Arity)

### 17. [KnowledgeBase/indexing] retract/1 of a rule (Head :- Body) never matches: KB unifies whole clause term against head only
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/KnowledgeBase.java:506-527`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: retractAllClausesWithBindings (and retractClauseWithBindings) only unify the incoming `term` against `rule.getHead()`. Retract.executeWithContext passes the entire clause argument unchanged, including the `Head :- Body` form. So `retract((H :- B))` tries to unify the compound `:-(H,B)` against the bare head `H`, which never succeeds, and no clause containing a body is ever retracted via the rule form. Verified empirically: with facts `foo(1):-bar(1). foo(2):-bar(2).`, `retract((foo(X):-bar(X)))` returns [] and removes nothing, whereas ISO requires both clauses to be retracted (binding X to 1 then 2). retract/1 for plain facts works only because the body is absent.
- **Fix**: Before unifying, decompose the retract pattern: if `term` is `:-(H,B)` then unify H against rule.getHead() AND B against the rule's body term (building 'true' for facts, or the conjunction of rule.getBody()); otherwise unify `term` against the head and require the rule body be empty/true. Do the head/body split either in KnowledgeBase.retractAllClausesWithBindings or in Retract.executeWithContext before calling the KB.

### 18. [List/String/Atom builtins] sort/2, setof/3 and friends silently delete elements that are numerically equal int vs float (standard-order int/float not distinguished)
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/list/Sort.java:128-132`  ·  **Category**: iso-conformance  ·  **Confidence**: high  ·  (orig sev: critical)
- **Problem**: Sort.compareTerms compares two Numbers purely by their double value and ignores Number.isInteger(). In ISO standard order, 1.0 and 1 are DISTINCT terms (float sorts before int when numerically equal). Because sort/2 dedups using compareTerms == 0, numerically-equal int/float pairs are collapsed and one is silently lost. Verified at runtime: sort([1.0,1],X) => X=[1.0]; sort([a,1,1.0],X) => X=[1,a] (1.0 lost); sort([3,1.0,1,2],X) => X=[1.0,2,3] (1 lost); setof(X,member(X,[1,1.0,1]),L) => L=[1] (1.0 lost). This is silent data loss. It also affects msort/2 ordering (msort([1,1.0]) vs msort([1.0,1]) yield different, input-order-dependent results instead of the canonical float-before-int order) and keysort/2.
- **Fix**: In the Number branch use Number.isInteger() as a tiebreaker after comparing values: int c = Double.compare(d1,d2); if (c != 0) return c; boolean i1 = ((Number)t1).isInteger(), i2 = ((Number)t2).isInteger(); if (i1 && !i2) return 1; if (!i1 && i2) return -1; return 0;  (per ISO, float @< int, so the float should compare as less). Better: delegate Sort.compareTerms to the single canonical StandardTermOrdering.compare after fixing that class (see related finding) so sort/2, @</compare/3 stay consistent.

### 19. [List/String/Atom builtins] StandardTermOrdering treats 1.0 and 1 as identical (compare/3 and @< wrong for numerically-equal int/float)
- **File**: `src/main/java/it/denzosoft/jprolog/builtin/term/StandardTermOrdering.java:98-101`  ·  **Category**: iso-conformance  ·  **Confidence**: high
- **Problem**: compareNumbers (lines 86-92) DOES intend to order integer before float for equal values, but its isInteger() helper re-derives integer-ness from the double value (val == Math.floor(val)) instead of reading the authoritative Number.isInteger() flag. Therefore 1.0 is misclassified as an integer and 1.0 vs 1 compares equal. Verified: compare(O,1.0,1) => O='=', and both 1.0 @< 1 and 1 @< 1.0 are false. - **Problem**: When the substitution is a plain HashMap (every BuiltInWithContext that calls solver.solve(goal, new HashMap<>(bindings), ...) — once, \+, ->, findall, etc. all pass plain HashMaps, and nested compound unify recurses with that same map), each compound unification copies the WHOLE binding map up front for rollback. For a deep nested term unified against a large accumulated substitution this is O(|substitution|) allocation per compound node, i.e. quadratic in pathological cases, and the snapshot is built even on the success path (then discarded). ### 91. [Engine perf] No tail-call/deterministic fast path for NON-last conjuncts: solveBodyGoals materializes full intermediate solution lists for every prefix goal
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/QuerySolver.java:937-959`  ·  **Category**: optimization  ·  **Confidence**: medium  ·  (orig sev: medium)
- **Problem**: The LCO trampoline (lines 791-934) fires only for the LAST body goal with exactly one input solution. For every NON-last body goal, the code allocates a fresh termSolutions ArrayList per input binding, fully enumerates that goal, and addAll's into nextSolutions — materializing the full cross-product of partial solutions for every conjunction prefix even when only one survives downstream. Combined with the recursionDepth cap of 2000 (line 159, ~4-5 Java frames/level), deeply nested non-tail recursion through conjunctions still grows the Java stack and hits the artificial limit / StackOverflowError before genuine exhaustion. So deep but shallow-branching programs thrash on intermediate-list allocation despite the existing narrow LCO.
- **Fix**: Extend the deterministic fast path beyond the last goal: when a non-last conjunct yields exactly one solution (the common deterministic case), continue in-place without allocating termSolutions/nextSolutions (carry currentBindings forward). Reserve list materialization for genuinely non-deterministic goals. This reduces allocation for deterministic conjunctions and lets the trampoline cover more of the body, easing the 2000-depth ceiling.

### 92. [Engine perf] Tabling fixpoint dedups answers via canonicalSol.toString() — full term String formatting per answer per iteration

### 94. [Resource leaks] StreamManager uses static non-synchronized HashMaps for all stream state — data races and corruption under concurrency

### 97. [Resource leaks] WithOutputTo captures System.out process-globally without synchronization — concurrent goals corrupt each other's output and can leak the swap

### 99. [SLD/cut/backtracking] recursionDepth reset to 0 on StackOverflowError corrupts the counter for still-active outer solve frames
- **File**: `src/main/java/it/denzosoft/jprolog/core/engine/QuerySolver.java:188-219`  ·  **Category**: bug  ·  **Confidence**: high
- **Problem**: solve() wraps every solveInternal call, so it appears at many nested levels of the recursion. If a genuine Java StackOverflowError is thrown deep in the stack, the innermost solve() catch sets the shared instance field recursionDepth = 0 and rethrows a PrologException. As that PrologException unwinds, every outer solveInternal frame still executes its `finally { recursionDepth--; }` (line 217), decrementing from 0 downward — leaving recursionDepth at a large NEGATIVE value once control returns to the top. The public solve(Term) entry point (lines 77-92) does not reset recursionDepth, so subsequent queries start from a negative base, effectively disabling the MAX_RECURSION_DEPTH guard (the limit check `recursionDepth > MAX_RECURSION_DEPTH` is then far harder to reach). In practice the MAX_RECURSION_DEPTH=2000 soft limit usually throws a clean PrologException before a real Java SOF, so this is hard to trigger and was not reproduced under default -Xss; hence low severity. But with deep non-recursion-counted frames (built-ins, trampoline) a true SOF can still occur, and the reset-then-decrement underflow is a real latent corruption.
- **Fix**: Do not mutate the shared counter from the catch in the middle of an unwinding stack. Remove `recursionDepth = 0` from the StackOverflowError handler (the per-frame `finally { recursionDepth-- }` blocks already restore it as the stack unwinds), OR reset recursionDepth = 0 at the top-level public solve(Term query) entry point (around line 81 alongside Trail.clear()) so each top-level query starts from a known-clean base regardless of how the previous one terminated.
